Q037｜Tool misuse 怎么防？

topic:: Tools

level:: Senior

type:: Security

source:: 16 高频面试题库

related:: 20_Projects/rich-interview/10-Knowledge/08-Agents-Tools-Function-Calling, 20_Projects/rich-interview/10-Knowledge/13-Safety-Security-Governance

status:: practiced

last_reviewed:: 2026-04-28

next_review:: 2026-04-29

中文理解

  • 工具 allowlist、权限校验、参数 validation、risk-based confirmation、sandbox/dry-run、rate limit、human approval、audit log。LLM 只能提出调用意图，真正执行由 deterministic policy gate 控制。

English concise bullets

  • Definition: Tool misuse means the model calls the wrong tool, uses unsafe parameters, repeats actions, or performs an action the user/system did not authorize.
  • Mechanism: Separate tool-call intent from execution. The LLM proposes an action; a deterministic policy gate validates tool allowlist, user permission, parameter schema, risk level, idempotency, rate limit, and confirmation requirement.
  • Tradeoff: More controls reduce autonomy and add latency, but they are necessary for tools with side effects, sensitive data, or enterprise permissions.

45-sec interview answer

To prevent tool misuse, I would not let the LLM directly execute tools. I would separate intent generation from execution. The model can propose a structured tool call, but a deterministic policy gate should validate whether the tool is allowed, whether the user has permission, whether the parameters match the schema, and whether the action is risky. For read-only low-risk tools, automatic execution may be fine. For actions like sending emails, deleting data, making purchases, or changing permissions, I would use dry-run, sandboxing, idempotency keys, and human confirmation. In production I would trace every tool call and evaluate tool selection accuracy, parameter correctness, side-effect safety, latency, and policy violations.

Follow-up questions

  • Where is the boundary between model decision and system execution?
  • Which tools require dry-run or human confirmation?
  • How do you make retries safe for tools with side effects?
  • How would you evaluate tool safety in production?

我的回答记录

  • Round 1：可以讲出 allowlist / policy gate / confirmation，但需要更自然地说出 “separate intent from execution”。
  • 卡住点：容易只罗列 controls，缺少 architecture boundary。
  • 改进句：The model proposes; the policy layer disposes.

Q038｜Multi-agent 有什么问题？什么时候不该用？

topic:: Agents

level:: Senior

type:: Tradeoff

source:: 16 高频面试题库

related:: 20_Projects/rich-interview/10-Knowledge/08-Agents-Tools-Function-Calling

status:: practiced

last_reviewed:: 2026-04-28

next_review:: 2026-04-29

中文理解

  • Multi-agent 不是默认升级。它适合任务可拆、角色边界清楚、共享状态可控的场景；不适合路径明确、风险高、强审计、低延迟或成本敏感的场景。主要风险是 coordination overhead、context bleed、重复工作、责任不清、错误传播、成本/延迟失控。

English concise bullets

  • Definition: Multi-agent means multiple agents with separate roles coordinate on a task, usually through shared state, task envelopes, or a coordinator.
  • Mechanism: Use role separation, shared task board, explicit ownership, memory isolation, status transitions, and audit logs. Do not let agents freely chat and trigger each other without boundaries.
  • Tradeoff: Multi-agent can improve specialization and parallelism, but it increases coordination cost, observability burden, and failure propagation risk.

45-sec interview answer

I would not use multi-agent by default. Multi-agent systems are useful when the task is naturally decomposable, such as research, planning, implementation, and review, and when each agent has a clear role and output contract. But they can fail through coordination overhead, duplicated work, context leakage, role confusion, and error propagation. For production, I prefer a deterministic workflow or state machine when the path is known or the task is high risk. If I do use multiple agents, I would add a coordinator, shared task state, per-agent memory boundaries, clear ownership, audit logs, and verification gates. I would evaluate task success, unnecessary actions, handoff failures, cost, latency, and safety violations.

Follow-up questions

  • What tasks are actually decomposable enough for multi-agent?
  • How do agents share task state without sharing private memory?
  • How do you avoid duplicate work and file conflicts?
  • When would a simple workflow be better?

我的回答记录

  • Round 1：核心立场要先说：not by default; workflow first。
  • 卡住点：容易把 multi-agent 讲成“更强”，但没讲 coordination cost。
  • 改进句：Multi-agent is an organizational pattern, not a quality guarantee.

Q039｜MCP 解决什么问题？和普通 tool calling 区别？

topic:: MCP

level:: Senior

type:: Concept

source:: 16 高频面试题库

related:: 20_Projects/rich-interview/10-Knowledge/08-Agents-Tools-Function-Calling

status:: practiced

last_reviewed:: 2026-04-28

next_review:: 2026-04-29

中文理解

  • Function calling 是模型/API 层表达“我想调用某个工具及参数”的结构化格式；MCP 是协议层，用来把 tools、resources、prompts、context 暴露给 AI client。真正的 agent runtime 还要负责规划、权限、执行、确认、审计、重试和恢复。不要说 MCP 替代 function calling，它们不是同一层。

English concise bullets

  • Definition: Function calling is a model/API format for tool-call intent; MCP is a protocol layer for exposing tools, resources, prompts, and context to AI clients.
  • Mechanism: Model emits a call intent; MCP standardizes what tools/resources are available; runtime enforces policy, executes calls, handles errors, and logs traces.
  • Tradeoff: MCP improves interoperability and tool discovery, but it does not remove the need for runtime permission control, schema design, confirmation, and eval.

45-sec interview answer

MCP and function calling solve related but different problems. Function calling is usually the model or API format that lets the model express a structured tool-call intent, such as the tool name and arguments. MCP is a protocol layer for exposing tools, resources, prompts, and context to an AI client in a standardized way. But neither of them alone is the full agent runtime. In production, the runtime still needs to choose tools, validate parameters, enforce permissions, request confirmation for risky actions, execute the call, handle errors, and log audit traces. So I would not say MCP replaces function calling. MCP standardizes tool and context access; function calling expresses intent; the runtime owns policy and execution.

Follow-up questions

  • What layer owns permission enforcement?
  • Does MCP replace function calling?
  • How do you evaluate an MCP-based tool ecosystem?
  • What can go wrong when too many tools are exposed?

我的回答记录

  • Round 1：要牢牢记住三层：protocol / intent format / runtime policy。
  • 卡住点：容易把 MCP 讲成“新的 tool calling”。
  • 改进句：MCP exposes capabilities; function calling requests actions; the runtime governs execution.
